# 第一部分：人话版

## 1. 这个系统是干什么的

### 1.1 一句话

把电商客服机器人从"按固定剧本走流程的 V1"升级为"会自己查订单、自己组合动作、说的每个数字都有工具结果背书的智能客服 V2"，并用同一套评测题证明 V2 比 V1 强。

### 1.2 它不干什么

| 不做的事 | 为什么不做 |
|---|---|
| 不改前端和数字人页面 | V2 对外接口契约照抄 V1，前端零改动本身就是验收项 |
| 不做人工坐席/工单系统 | 转人工仅保留引导话术，真实坐席不在范围 |
| 不接真向量库 | 知识检索层默认用固定 FAQ 占位实现，接口已预留，换库只换 Provider |
| 不引入 PostgreSQL / Redis / 异步 worker | 保持 MySQL + 单进程直处理，控制复杂度（主动砍掉，理由见 13.2） |
| 不做多智能体协作 | 单 agent + 技能收窄已覆盖全部 6 类业务，多智能体徒增调试与评测成本 |
| 不重写电商业务后端（18081） | V2 只做它的调用方 |

### 1.3 系统最值钱的地方

用户说"我上周买的杯子碎了，想退钱"。V1 里这句话必须正中某个预设意图才走得动，答错一步就进澄清死胡同。V2 里智能体自己：加载退款技能 → 查订单 → 复述订单让你确认 → 问清退款原因 → 提交退款单——全程它说的**每个订单号、每笔金额、每个状态**都必须能对上本次对话里工具查回来的真实结果，**编造会被服务端当场拦截并自动纠错重答**。这套"执行时取证 + 事实检验 + 纠错闭环"是 V1 完全没有的能力，也是面试时最能展开讲的部分。

### 1.4 为什么值得升级（价值论证）

| V1 的结构性缺陷 | V2 怎么补 |
|---|---|
| 意图路由"一次定生死"：每轮一次分类，分错即进澄清 | agent 自主决策 + 技能收窄，允许边走边修正 |
| LLM 只能发 4 种固定命令，不能组合动作 | 原生 tool calling，一次诉求可编排多工具 |
| 业务知识散在 YAML 流程 + Python Action 两处 | 知识集中到 Skill 定义（四段式 guidance），工具独立注册 |
| 无运行观测，出问题靠翻日志 | 每次 Run 落库（tokens / 延迟 / 模型 / prompt 版本 / 工具快照） |
| 知识库空壳；路由准确率、槽位成功率从未量化 | 50 条分维度评测集 + 双版自动跑分，升级效果有数字 |
| 多轮状态整份 JSON 存库，写放大、易丢更新 | 只存消息历史，业务数据现查现用 |

## 3. 一次完整的使用过程（演示剧本）

场景：顾客小李上周买的保温杯坏了想退款，顺便想让推荐个新的。

| 步 | 谁 | 做了什么 | 系统里发生什么 |
|---|---|---|---|
| 1 | 小李 | 打开客服窗说"上周买的保温杯坏了想退款" | WS 建连，消息落库，创建 Run#1（RUNNING） |
| 2 | 引擎 | — | 未激活技能 → 提示词只有技能索引，模型调 load_skill(REFUND)，可见工具收窄为退款相关 |
| 3 | 引擎 | — | 无订单号 → 调 list_orders 查订单列表（P1 条件工具，见 FR-203） |
| 4 | 小李 | 点选"保温杯"订单卡片 | 对象消息注入上下文，订单号参数就位 |
| 5 | 引擎 | — | 调 get_order 成功 → 快照落库；回复复述订单信息并询问退款原因 |
| 6 | 小李 | "杯盖裂了，漏水" | 参数齐 → Run#1 置 AWAITING_CONFIRM，回复"将提交退款：订单X、原因杯盖裂，确认吗？" |
| 7 | 小李 | "确认" | 新 Run 识别待确认意图 → 调 submit_refund_application → 成功 → Run#2 COMPLETED，返回退款单号 |
| 8 | 小李 | "几天能到账？" | 切到政策知识技能 → search_knowledge（固定 FAQ 占位）→ 回答并附来源条目 |
| 9 | 小李 | "推荐个新杯子" | 切到商品咨询技能 → recommend_similar_products → 商品卡片 |
| 10 | 小李 | "顺便编个 500 块的退款试试" | 事实检验发现 500 无工具结果背书 → 纠错重答，拒绝编造 |
| 11 | 开发者 | 会后打开 agent_runs 表 | 看到 4 条 Run 记录：tokens、延迟、工具调用快照、prompt_version |
| 12 | 开发者 | 跑评测脚本 | 同一 50 条题库分别打 V1 与 V2，产出对比报告 md |

**演示演几幕**：①售后退款全流程（约 2 分钟）；②"诱导编造"展示事实检验拦截（30 秒）；③观测表 + 评测对比报告（1 分钟）。
**演示避坑**：提前造好测试订单与退款数据；先起 docker MySQL 和 18081 业务服务并验证连通；"诱导编造"话术提前演练过一次；断网演示工具失败降级前先在本地试一遍。

## 4. 系统有哪些功能（6 块）

**4.1 智能体对话引擎（harness）**：以 langchain v1 `create_agent` 为骨架（与课程一致），自研三个中间件——动态提示词（每次模型调用按当前技能重渲染三层提示）、技能工具收窄（未激活只给 load_skill，激活后只给该技能的工具集）、调用上限（单 Run 工具调用 ≤8 次，超限固定话术收尾）。纠错循环：输出校验不过 → 带反馈消息重跑，上限 2 次，复用完整消息轨迹。

**4.2 工具层**：统一信封 `ToolResult{success, code, message, data, failure_type}`——工具永不向模型抛异常；执行前后落库快照；页面动作白名单——模型只能报"卡片编码 + 资源ID"，卡片内容由服务端组装（沿用 V1 前端现有对象协议）。

**4.3 技能（Skill）**：5 个业务技能 + 闲聊兜底：商品咨询 / 订单查询 / 物流售后 / 退款 / 政策知识。每个技能的 guidance 四段式：查询入口 / 工具选择 / 可信依据 / 边界处理。

**4.4 校验层**：结构化输出（回复类型 ANSWER/CLARIFY/DECLINE/REQUEST_HANDOFF + 可选页面动作）；事实检验（编号/金额/状态三类事实必须有本 Run 成功工具结果背书）；纠错反馈消息；业务工具全失败时固定降级话术。

**4.5 记忆与观测**：MySQL 三张表——消息历史（重建上下文）、agent_runs（Run 生命周期与用量）、agent_tool_calls（工具调用快照）。历史裁剪三层：条数上限 → 字符预算 → 从首条用户消息保留；未完成任务摘要随上下文注入。

**4.6 评测体系**：50 条分六维度题库（正常路径 / 缺槽位反问 / 打断恢复 / 多意图 / 越界输入 / 闲聊知识）；HTTP 黑盒脚本同时打 V1 与 V2；确定性指标用规则断言，回答质量用 LLM-judge；产出对比报告 md。

**4.7 技术设计点（"技术难点在哪"的答案）**

1. **上下文工程**：技能收窄 + 三层裁剪 + 动态重渲染——在单 agent 架构下同时控制 token 成本与选错工具率，这是"让一个 agent 稳定覆盖 6 类业务"的核心手段。
2. **执行时取证**：工具调用即落库快照，事实校验的证据源与 agent 循环完全解耦——校验器不信任模型的自述，只信任落库的执行记录。
3. **错误码二分的纠错闭环**：可纠正错误（模型输出不合规范）→ 带反馈重跑；终态错误（基础设施故障）→ 稳定错误码落库。两条路径绝不混淆，也绝不向模型泄漏异常堆栈。
4. **信封化工具层**：模型只见结构化成败，不见异常——从机制上消灭"模型看到 traceback 开始胡编"这类最难排查的故障。

## 9. 核心规则明细

### 9.1 ToolResult 信封（JSON 示例）

```json
{"success": false, "code": "EC-3001", "failure_type": "SERVICE_CALL",
 "message": "订单服务暂时不可用，请稍后再试", "data": null}
```

### 9.2 事实提取与比较

- 编号：正则 `ORDER_\d+`、`AS_\d+`、退款单号前缀（以 18081 实际格式为准）。
- 金额：`¥?\d+(\.\d+)?\s*(元|块)` 及"金额/价格/运费"语境数字 → Decimal 精确等值。
- 状态：中文状态词集合与 18081 状态枚举对齐（建映射表，M1 核实后固化）。
- 归一化：NFKC + casefold + `-`→`_`；证据 = 本 Run success=true 的工具调用 arguments+result 递归标量。

### 9.3 可配置参数表（均为示例默认值，与课程对齐）

| 参数 | 默认值 | 位置 |
|---|---|---|
| history_message_limit | 30 条 | config |
| history_character_budget | 12000 字符 | config |
| max_correction_attempts | 2 | config |
| tool_call_limit（单 Run） | 8 | config |
| 单轮 LLM 调用上限 | 4（1 主调用 + 2 纠错 + 1 收尾） | config |
| 工具执行超时 | 10 s | config |
| 流式首包目标 | ≤2 s（受 qwen 网络影响） | NFR-01 |

### 9.4 对话级二次确认规则（退款）

1. submit_refund_application 仅在"参数齐 + 本 Run 存在 AWAITING_CONFIRM 且其 result 中的订单/原因与本次参数一致"时执行；
2. AWAITING_CONFIRM 的产生：agent 判断参数已齐 → 不调写工具，回复复述摘要并置 Run 状态；
3. 下一 Run 组装上下文时注入"上轮有待确认退款（订单X/原因Y）"；模型识别确认语义 → 调写工具；识别为改参数 → 更新后重新进入流程；识别为无关话题 → 旧 Run 置 SUPERSEDED。

### 9.5 模型使用边界

- **用模型**：意图理解、参数抽取、回复生成、纠错重答。
- **绝不用模型**：金额计算与比较（Decimal）、状态判断（枚举映射）、卡片 URL/文案（服务端拼装）、事实真伪（落库证据比对）。

## 10. 状态机与流转

agent_runs.state 取值（就这 5 个，不多不少）：

| 从 | 到 | 什么时候 |
|---|---|---|
| （创建） | RUNNING | Run 创建即进入 |
| RUNNING | AWAITING_CONFIRM | 参数已齐，等待用户对话确认写操作 |
| RUNNING | COMPLETED | 输出校验通过，无待确认写操作 |
| RUNNING | FAILED | 终态错误（EC-2xxx） |
| AWAITING_CONFIRM | COMPLETED | 确认后写工具执行成功 |
| AWAITING_CONFIRM | SUPERSEDED | 用户转向其他话题（由后续 Run 判定并回写） |

其他任何流转一律拒绝（状态机单测覆盖非法流转）。
